# DroidSeal Threat Model · 加固层威胁模型

[中文](threat-model.zh-CN.md) | [English](threat-model.md)

本文档描述 DroidSeal 加固层(P0-A/B/C、P1、P2)的攻击面、防御机制与**如实标注的残余风险**。原则与整个项目一致:未实现的能力不声称,运行时行为无法构建期验证的如实标注。

**适用范围**:仅 `harden` 流水线产物(显式 opt-in 的 release APK 加固)。审计/签名/验证流程不涉及运行时防御,不在本文档范围。

**对抗者模型**(由弱到强):

| 等级 | 对抗者 | 能力 |
|---|---|---|
| A | 脚本小子 | 公开工具重打包、重签名、改资源 |
| B | 动态分析者 | Frida/Objection attach、hook、内存读写;无 root 或临时 root |
| C | 逆向工程师 | IDA/Ghidra 静态分析、自定义 Frida 脚本、root 设备持久访问 |
| D | 国家级/资源充足 | 定制 ROM、内核级工具、硬件调试、无限时间 |

**防御目标**:使 A 必败、B 的常规路径产生错误结果而非可绕过的警告、C 的成本显著抬升。**明确不防御 D**。

## 攻击面 → 防御

### AT-1 · 重打包/重签名(对抗者 A)

**攻击**:修改 APK 内容(注入代码、篡改资源、去除校验)后用自己的 key 重签名,分发破解版。

**防御(P0-A 完整性锚点)**:最终二进制 `AndroidManifest.xml` 的 SHA-256 在加固流水线 Step 4 计算并折入**每个条目**的 HKDF info(`dex-N`/`citable`/`so` 均)。运行时 `computeIntegrityAnchor` 重算比对。任何重打包必改 manifest → 派生密钥与加密时不同 → AES-256-GCM 认证失败 → 解密静默失败(fail-closed)。

**性质**:密钥化——攻击者 patch 掉比较逻辑也无法"通过校验",因为校验结果就是密钥本身的一部分;没有"校验失败但仍解密"的路径。

### AT-2 · 调试器/Frida attach(对抗者 B)

**攻击**:不修改 APK,直接 attach Frida/调试器,在运行时读取内存中的密钥或明文 DEX。

**防御(P0-B 环境门控 + P1 三源投票)**:启动时三源异构检测——Java 侧(`DroidSealGuard`)、native 侧(fork 子进程读父进程 `/proc/<ppid>/status` TracerPid + Frida 端口 27042/27043 探测 + maps 扫描)、debuggable 标志。投票结果以 `-e<vote>` 后缀折入 HKDF info:检测命中 → 派生错钥 → GCM 静默失败。

**性质**:攻击者 hook 掉单个检测源,另两源仍投污染票;hook 掉全部源=恢复"干净"派生(见 AT-4)。不 attach 直接跑则完全正常——误伤面控制见残余风险 R-1。

### AT-3 · 静态分析(对抗者 B/C)

**攻击**:jadx/Ghidra 打开 APK,直接读 DEX 字节码找业务逻辑。

**防御(三层叠加)**:
1. **方法抽取**:CodeItem 挖空,方法体以加密 CodeItem 表(`citable` 条目,独立 per-entry 派生密钥)存于容器,运行时 ART DefineClass 钩子按表写回。抽取覆盖率逐构建量化输出(`DEX_METHOD_HOLLOW` finding:`hollowed/total`),不虚报"全保护"。
2. **DEX 整体加密**:loader DEX(密钥+解密逻辑)以 HKDF(签名证书摘要)派生密钥 AES-256-GCM 加密存于 `.ldx` asset(stored);明文 `classes.dex` 仅含随机化类名的引导 stub。
3. **类名/标识符随机化**:stub/loader 标识符逐构建随机,消除静态签名定位。

**性质**:静态拿到的永远不是完整明文——CodeItem 表与 DEX 分属不同密钥条目。

### AT-4 · patch 掉检测(对抗者 C)

**攻击**:逆向找到检测代码,patch 掉(改 smali/二进制),让环境"看起来干净"。

**防御**:这是 P0-B 的设计核心——patch 检测**恢复了正确密钥派生**,攻击者拿到的是与原版一致的产物,不亏不赚;但 patch 本身改了 DEX/manifest → 触发 AT-1 锚点 → 错钥。两条路径交叉:patch 检测必须同时绕过锚点(重打包),而锚点无法 patch(密钥在加密时已定型)。攻击者要么整包重加密(等价于自己重新实现壳),要么放弃。

**如实边界**:见 R-3——C 级攻击者最终可从内存 dump 拿到明文。

### AT-5 · 密钥提取(对抗者 C)

**攻击**:内存扫描找完整 master 密钥。

**防御(P0-C 分片化)**:master 不常驻内存——三段式 `part1 ⊕ part2 ⊕ part3`,part2 可注入 native SO(CI 用真实 NDK 编译验证),part3 可选剥离出 APK(P2);运行时逐条目临时合成 → 派生 → 立即清零;解密后 DEX 缓冲类加载完成后即刻清零。

**性质**:任意时刻内存无完整 master;但见 R-3 的 dump 窗口说明。

### AT-6 · 设备外扩散(对抗者 A/B)

**攻击**:合法设备上提取产物后,复制到其他设备运行。

**防御(可选 `--keystore-bind`)**:首次解密成功后以 Android Keystore 封存 pre-XOR part1′ 并抹掉嵌入值;卸载重装/清数据/换机后 Keystore 不可用 → 解密失败。与 P2 挑战模式组合兼容(封存值与 XOR 顺序严格一致,SEC-003 修复后路径一致)。

**性质**:一机一份是产品语义而非漏洞——需在发布时明示用户(已写入 README/CLI 警告)。

## 残余风险(如实,不可消除项)

| # | 风险 | 等级 | 说明 |
|---|---|---|---|
| R-1 | 环境误伤 | 低 | Frida 端口探测(27042/27043)在同设备跑多实例时可能误报——技术无解,已如实写入 README;误伤行为是"解密失败"而非崩溃,可通过去除 Frida 验证 |
| R-2 | 端口探测无法区分目标 | 低 | 无法区分"对本 App 的 Frida"与"对同设备其他 App 的 Frida"——按保守方向设计(宁可误杀不漏放) |
| R-3 | 内存 dump | **不可完全防** | root + 持久物理接触下,C 级攻击者可 dump 解密后的 DEX(明文窗口以"类加载完成后即刻清零"最小化,但窗口存在);密钥在派生瞬间必然短暂完整存在于内存。**这是所有非 VMP/非白盒方案共同的上限**,本项目的取舍是不投入白盒 AES/VMP(成本高、兼容性差、且对 D 级攻击者同样可破) |
| R-4 | 延迟销毁可被绕过 | 低 | 检测命中后的延迟自毁可被 hook `System.exit` 绕过——但绕过只救回"检测已暴露"的会话,密钥仍是错的,不产生信息泄露 |
| R-5 | minSdk<26 落盘路径 | 低 | API<26 走落盘 DexClassLoader 降级,加密 loader 落盘文件可被 root 提取(提取到的是密文,且 stored 直读依赖已由产物基线 H2 保证) |
| R-6 | 深度定制 ROM | 低 | ActivityThread 反射在极端定制 ROM 可能返回 null——已有 appContext 优先注入 + fail-closed(不崩溃,解密失败) |
| R-7 | 挑战端点可用性 | 模式性 | `--challenge-url` 模式下端点成为运行时依赖:离线/端点丢失 → 解密失败(fail-closed,不降级);`server-challenge.json` 丢失 = 该构建永久无法解密,需离线备份 |
| R-8 | 真机矩阵未完成 | 验证性 | 构建期全部可验证项已绿(264 测试 + H1–H6 基线 + CI NDK 编译)。**模拟器验收(API 26 x86_64,2026-09)已完成**:首轮在构建期全绿的情况下首启即崩——链式暴露三个构建级缺陷并全部修复([SEC-010/011/012](security-ledger.zh-CN.md));修复后 D1/D2/D3/D5 PASS(含二次启动复核)。尚未覆盖:真机矩阵、KS 绑定二次启动(D4)、API 24 落盘降级路径——见 `docs/device-testing.md`(含实测记录) |

## 附录 · 审计侧攻击面扩展(2026-09-26)

加固层威胁模型之上,审计引擎近期扩展了三类 native 攻击面可见性(审计 finding,不改变加固行为):

- **JNI 动态注册恢复**(JNI_DYNAMIC_REGISTER):SO 字符串池注册表痕迹 + DEX 双命中交叉验证——动态注册的 native 方法无 Java_ 静态导出符号,此前对 AT-3(静态分析对抗者)视角不可见;
- **native 线性数据流**(NATIVE_DATAFLOW_SUSPECT):JNI 导出函数体 source→sink 共现,**线性启发式、confidence: low**——仅人工核验线索,非指针分析,不作为判定依据;
- **混淆名归一**(对判层):方法体唯一 API 锚定,歧义如实放弃——影响 bench 口径,不影响运行时行为。

如实边界:三者均为检测/对判层增强;mProtected 在真机矩阵验收前恒 false,里程碑 B(RegisterNatives 桥)仅为构建期代码路径。
